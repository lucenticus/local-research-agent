## Важное уточнение: три пути retrieval, не один

Правило «don't index everything» относится **только к research-funnel**. Всего путей три:

1. **research (funnel)** — JIT: discovery → triage → deep-read выживших. Индекс не строится заранее.
2. **`ask`** — локальный RAG поверх **заранее построенного** индекса (`cli index`). Индекс здесь — сознательно.
3. **digest** — своя Qdrant-коллекция, hybrid → rerank, **без** funnel (нет подвопроса, к которому мерить релевантность).

Это не противоречие, а три режима под три задачи. На собеседовании вопрос «почему тут индекс, а там JIT?» прилетит первым — ответ выше.

## Backlog «что осталось» (приоритет сверху)

### 1. Офлайн eval-харнесс — узел 22 *(наибольшая ценность)*
В репо уже есть `agent/evaluate.py` — но, судя по расположению в `agent/`, это оценка **одного прогона** (само-верификация/faithfulness внутри пайплайна), а не бенчмарк. Трейсинг показывает *что произошло*, evaluate.py — *насколько хорош этот ответ*, но ни то ни другое не отвечает на *стало ли лучше после правки*. Нужен регресс-прогон на фиксированном наборе.
- `evals/questions.jsonl`: 10–20 золотых вопросов с ожидаемым покрытием подтем.
- Метрики: **coverage** (закрыты ли подтемы), **faithfulness** (переиспользовать скореры из `agent/evaluate.py`, не дублировать), **cost** (вызовы/токены), **latency** p50/p95 по стадиям.
- `evals/run_eval.py`: прогон на фикстурах, таблица метрик, **дифф против прошлого прогона**.
- *Почему первым:* дёшево, ловит регресс, переиспользует существующий `evaluate.py`, и это ровно тот артефакт, который просят на интервью («как измеряешь качество агента»).

### 2. Complexity Router — узел 2
Сейчас выбор `ask`/`research` ручной. Добавить лёгкую развилку на входе.
- Классификатор `answer_directly / search / clarify` (можно кодом + порогами, без нового LLM-резидента).
- Метрика узла: precision/recall решения о поиске.
- *Осторожно с памятью:* не тянуть вторую резидентную модель — решать кодом/эвристикой или bounded-вызовом уже загруженной 4B.

### 3. Расширить Recovery — узел 8
- Пустой/мусорный discovery → переформулировать подвопрос / сменить источник (а не просто пустой результат).
- Противоречия между источниками → предъявлять в отчёте, не «усреднять».
- Circuit breaker на нездоровый источник (один упавший API не роняет запрос).

### 4. Проверить по коду (не по CLAUDE.md)
- Узел 5: есть ли переписывание запроса под источник и повтор при промахе?
- Узел 1: обрабатывается ли кореференция в многотуровом диалоге?
- Узел 16: как деградирует извлечение на LaTeX-формулах/таблицах?
- Узел 19: используется ли свежесть как сигнал ранжирования?
- Узел 21: кэшируются ли ответы discovery-API?
- Узел 22: `agent/evaluate.py` — оценка одного прогона или уже офлайн-бенчмарк? от этого зависит объём пункта 1.

### 5. Housekeeping (мелочь)
- В `src/store/__pycache__` висит `lancedb_store.cpython-312.pyc`, но `lancedb_store.py` в исходниках нет — мёртвый артефакт после миграции LanceDB→Qdrant. Удалить `.pyc` (или почистить `__pycache__`), чтобы не путал.

## Как отдать это в Claude Code

Система уже стоит, поэтому не «строим по плану», а точечные задачи. Порядок работы из твоего
CLAUDE.md («implement → stop → show diff → wait for review», DoD на реальном железе) — сохраняется.

Пример задачи под первый пункт backlog:
> Прочитай CLAUDE.md. Добавляем eval-харнесс (узел 22). Сначала предложи схему `evals/questions.jsonl` и набор метрик (coverage, faithfulness, cost, latency) — согласуем формат до кода. Faithfulness переиспользуй из существующих эвристик в `agent/loop.py`, не дублируй. Тесты офлайн, на фикстурах. Остановись на ревью схемы.
